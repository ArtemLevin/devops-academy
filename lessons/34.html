01 · Что требуется уметь

Цель и критерий результата

Тема: RPO/RTO и планы. Измеримая цель: Спроектировать восстановление и метрики.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. RPO — максимально допустимая потеря данных по времени, RTO — максимально допустимое время восстановления сервиса.
  2. Политика backup должна учитывать частоту, целостность, ключи шифрования, срок хранения и возможность выполнить restore на отдельном стенде.
  3. Не всякая копия является восстановимой: проверка доступности объекта и тестовый restore имеют разную доказательную силу.

Три конкретных примера

1. Учебные значения RPO/RTO

Пример: text
Last backup: 12:00
Failure:     12:17
Restored:    12:43
Data loss window ≤ 17 min (если backup валиден)
RTO observed: 26 min

Как интерпретировать: Уточните start и end таймера. Политика целевых значений задаётся отдельно от результатов drill.

2. Шаблон плана

Пример: yaml
scope: synthetic-postgres
rpo_target_minutes: 30
rto_target_minutes: 60
backup_verification: checksum-plus-restore
recovery_owner: training-operator

Как интерпретировать: Документ описывает безопасный учебный стенд; не содержит учетных данных и реальных данных.

3. Проверка контрольной суммы тестовой копии

Пример: bash
sha256sum ./synthetic-backup.dump

Как интерпретировать: Хеш выявляет изменение файла с момента снятия эталона, но не доказывает логическую корректность данных внутри.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

RPO/RTO измеряются в разных единицах

RPO (Recovery Point Objective) — допустимая потеря данных по времени между последним восстановимым состоянием и аварией. RTO (Recovery Time Objective) — допустимая длительность восстановления сервиса. Для критических данных маленький RPO требует более частых snapshot или журналирования изменений; быстрый RTO требует предварительно проверенного сценария восстановления.

Факт существования backup ещё не доказывает его пригодность. Нужны доступный носитель, ключи, совместимая версия инструментов и результат test restore с контрольными данными.

Backup: 11:00
Incident: 11:37
Latest restorable point: 11:00
Observed data gap: 37 min
Restored service: 12:25
Observed recovery duration: 48 min

from datetime import datetime
fmt = '%H:%M'
gap = datetime.strptime('11:37',fmt) - datetime.strptime('11:00',fmt)
print(gap.total_seconds()/60, 'minutes')  # 37

Приём: указывайте RPO/RTO в явных единицах и отдельно цель/факт. Ловушка: считать 37 минут обязательной потерей данных, если доступны другие журналы/реплики. Проверка: сравните целевые метрики с измеренными только на тестовом drill.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Резервные копии регулярно создаются, но тест восстановления никогда не проводился.

Диагностическая развилка

Потребуйте restore drill в отдельной среде, сверку инвариантов и измеренный RTO; не принимайте cron success за recovery evidence.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Считать расписание backup достаточной гарантией восстановления.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Предложите RPO/RTO для синтетической очереди заданий и допустимый порядок восстановления компонентов.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Резервные копии регулярно создаются, но тест восстановления никогда не проводился.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему считать расписание backup достаточной гарантией восстановления — неверный диагностический вывод?
Показать критерий хорошего решения

Потребуйте restore drill в отдельной среде, сверку инвариантов и измеренный RTO; не принимайте cron success за recovery evidence.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
