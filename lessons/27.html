Парное сравнение

01 · Что требуется уметь

Цель и критерий результата

Тема: Парное сравнение. Измеримая цель: Оценить различия baseline/candidate с шумом.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Парное сравнение уменьшает шум: baseline и candidate измеряют в сопоставимых условиях и сохраняют пары результатов.
  2. Абсолютная разница, относительное изменение и разброс отвечают на разные вопросы; проценты требуют явного знаменателя.
  3. Регрессия должна превышать обычный шум измерения и быть значима для пользовательского сценария.

Три конкретных примера

1. Парные времена ответа в миллисекундах

Пример: python
baseline=[120,115,130,124,118]
candidate=[110,112,125,117,113]
delta=[c-b for b,c in zip(baseline,candidate)]
print(delta,sum(delta)/len(delta))

Как интерпретировать: Отрицательная разница означает ускорение candidate. Это небольшой синтетический пример, недостаточный для серьёзного статистического вывода.

2. Формула изменения

Пример: text
relative_change_% = 100 × (candidate - baseline) / baseline
120 ms → 110 ms: 100 × (-10)/120 = -8.33%

Как интерпретировать: Не меняйте местами знаменатель и сравниваемую величину.

3. Обязательные поля отчёта

Пример: text
scenario | build SHA | browser | median | p95
runs | CPU noise | confidence/variation | raw trace

Как интерпретировать: Даже красивый график без raw data не позволяет воспроизвести результат.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Сравнение с шумом и неопределённостью

Производительность — случайно колеблющаяся величина. Для baseline и candidate используйте одинаковые синтетические сценарии, несколько прогонов и заранее определённую главную метрику. Медиана устойчива к отдельным выбросам, а p95 подчёркивает неприятные хвосты распределения; при малой выборке оценка p95 нестабильна.

Если улучшение сопоставимо с разбросом, корректное заключение — «данных недостаточно», даже если среднее уменьшилось.

from statistics import median
baseline = [23, 20, 24, 21, 22]
candidate = [20, 19, 22, 21, 20]
print('median baseline', median(baseline))
print('median candidate', median(candidate))

baseline (median): 22 ms
candidate (median): 20 ms
Разница: -2 ms
Дальше: оценить разброс и повторить на нескольких нагрузках

Приём: чередуйте прогоны A/B, чтобы дрейф температуры или фоновой нагрузки меньше искажал результат. Ловушка: выбирать метрику уже после просмотра цифр. Проверка: заранее записанные критерии, медиана, разброс и описание окружения.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

В dashboard p95 улучшился, но отдельные клиенты жалуются на задержку.

Диагностическая развилка

Проверьте перцентиль по сегментам, число измерений, разброс и возможную неоднородность устройств.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Объявлять выигрыш по среднему при росте p95 без оговорки.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Подготовьте парное сравнение синтетических серий и обоснуйте, допустим ли вывод об улучшении.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «В dashboard p95 улучшился, но отдельные клиенты жалуются на задержку.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему объявлять выигрыш по среднему при росте p95 без оговорки — неверный диагностический вывод?
Показать критерий хорошего решения

Проверьте перцентиль по сегментам, число измерений, разброс и возможную неоднородность устройств.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
