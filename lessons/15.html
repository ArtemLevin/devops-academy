Вызвать намеренный fail на тестовом PR. В этом материале разберём устройство механизма, примеры отказов и порядок подтверждения результата.

01 · Что требуется уметь

Цель и критерий результата

Тема: CI fault injection. Измеримая цель: Вызвать намеренный fail на тестовом PR.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Контролируемый CI-fault injection должен сломать ровно одну тестовую проверку в изолированной ветке, не повреждая реальные данные и секреты.
  2. Нужно доказать связь commit → тестовое условие → failure CI; после revert тот же gate обязан снова стать зелёным.
  3. Падение CI инфраструктурного происхождения (rate limit, downtime runner) отличается от функционального провала теста.

Три конкретных примера

1. Маленький тест с ожидаемым падением

Пример: python
def test_invariant():
    expected = 2
    actual = 1 + 1
    assert actual == expected

Как интерпретировать: Этот тест успешен. Для fault injection изменяйте только ожидаемое значение в отдельной учебной ветке.

2. Проверка теста до PR

Пример: bash
python -m pytest -q tests/test_invariant.py
git diff --check

Как интерпретировать: Команды только для учебного проекта с установленным pytest; фиксируйте exit code и место ошибки.

3. Таблица доказательств

Пример: text
BASE SHA   test_invariant PASS
FAULT SHA  test_invariant FAIL (assertion mismatch)
FIX SHA    test_invariant PASS

Как интерпретировать: Три результата должны иметь реальные run URLs. Не засчитывайте ручную симуляцию логов вместо CI.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Намеренный CI fail и полезная диагностика

Fault injection в CI проверяет, что пайплайн обнаруживает заранее определённую учебную неисправность. Она должна затрагивать только тестовую ветку/PR и синтетический тест, иметь заранее определённый способ отмены и не использовать секреты. Хороший эксперимент доказывает причинность: одна контролируемая ошибка меняет зелёный gate на красный, а её устранение возвращает зелёный результат.

Не смешивайте сбой самой инфраструктуры runner с падением проверяемого теста: они требуют разной диагностики.

# Запускается только в учебной копии, не в production-ветке
import unittest
class IntentionalFailure(unittest.TestCase):
    def test_training_gate(self):
        self.assertEqual(2 + 2, 5, 'training failure')

Run A / commit X: тест успешен
Run B / commit Y: AssertionError -> failure
Run C / commit Z: исправленный тест -> success
Артефакт: три URL run + сравнение diffs

Приём: меняйте ровно одну независимую переменную между B и C. Ловушка: считать любой красный pipeline доказательством работы quality gate; причиной мог быть сетевой сбой скачивания пакетов. Проверка: найдите конкретный assertion в логах.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Тестовый PR показывает красный CI после изменения тестового ожидания.

Диагностическая развилка

Сверьте вывод failure с diff и SHA; убедитесь, что причина — assertion, а не проблема установки пакетов.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Переносить fault injection в защищённую main-ветку или рабочую систему.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

В изолированной ветке внесите обратимую тестовую неисправность, покажите fail, восстановите и покажите pass.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Тестовый PR показывает красный CI после изменения тестового ожидания.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему переносить fault injection в защищённую main-ветку или рабочую систему — неверный диагностический вывод?
Показать критерий хорошего решения

Сверьте вывод failure с diff и SHA; убедитесь, что причина — assertion, а не проблема установки пакетов.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
