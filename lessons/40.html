01 · Что требуется уметь

Цель и критерий результата

Тема: VPS/SSH/HTTPS. Измеримая цель: Составить безопасную схему работы с VPS.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Для VPS определяйте схему доверия: SSH административный вход, firewall, DNS, обратный прокси и TLS termination; каждый слой имеет отдельную проверку.
  2. SSH-ключ подтверждает владение приватным ключом; приватную часть нельзя загружать в ChatGPT, CI-логи или общедоступные репозитории.
  3. Изменения firewall и SSH на удалённом сервере могут лишить доступа; необходим резервный путь через консоль провайдера и явное разрешение.

Три конкретных примера

1. Изучить известные SSH настройки без соединения

Пример: bash
ssh -V
ssh -G example.invalid | head -25

Как интерпретировать: Синтетический host example.invalid; `ssh -G` показывает эффективную клиентскую конфигурацию, не устанавливает соединения.

2. TLS-путь по уровням

Пример: text
client DNS → public IP → 443/TCP → TLS handshake
→ reverse proxy → 127.0.0.1:app_port → app
HTTP 502: upstream / proxy boundary to investigate

Как интерпретировать: Фактическое размещение proxy нужно сверить с конфигурацией сервера.

3. План безопасного изменения

Пример: yaml
change: "allow new SSH source"
rollback: "provider console + previous rules"
dry_run: "inspect current rules first"
approval_required: true

Как интерпретировать: Этот YAML — управленческий шаблон. Никаких изменений firewall в текущей задаче не выполняйте.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Доступ на VPS: сетевые границы и доверие к ключам

Эксплуатация удалённого сервера начинается с модели доступа: SSH-ключи, host key, минимальный набор открытых портов, ограниченные учётные записи, обновления и логирование. Предварительная проверка fingerprint нового сервера защищает от соединения с подменённым узлом; доверять приглашению yes/no без внешней проверки нельзя.

HTTPS подтверждает TLS-соединение с сервером при успешной проверке цепочки сертификатов и имени; оно не гарантирует безопасности самого приложения. Для новых релизов применяйте тестовый стенд и план отката.

ssh -G example.invalid | sed -n '1,18p'
# Только просмотр итоговой конфигурации клиента для учебного имени

Inbound policy (проект):
22/tcp: только админская сеть или bastion
443/tcp: публичный HTTPS
5432/tcp: не публиковать PostgreSQL
6379/tcp: не публиковать Redis

Приём: перед подключением проверяйте целевой host, fingerprint и роль ключа. Ловушка: случайно открытый PostgreSQL/Redis; firewall должен сочетаться с аутентификацией сервиса. Проверка: проводите плановое сетевое сканирование только собственного разрешённого тестового стенда.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

После изменения firewall пропало SSH-подключение; HTTP ещё работает.

Диагностическая развилка

Избегайте дополнительных изменений вслепую. Подтвердите доступ через out-of-band консоль и снимок прежних правил.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Менять SSH/firewall без рабочей резервной консоли.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Нарисуйте эксплуатационную схему VPS с сетевыми портами и безопасным recovery path.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «После изменения firewall пропало SSH-подключение; HTTP ещё работает.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему менять ssh/firewall без рабочей резервной консоли — неверный диагностический вывод?
Показать критерий хорошего решения

Избегайте дополнительных изменений вслепую. Подтвердите доступ через out-of-band консоль и снимок прежних правил.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
