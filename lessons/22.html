01 · Что требуется уметь

Цель и критерий результата

Тема: Release flow. Измеримая цель: Изучить staging, approval, immutable digests.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Release flow описывает входной SHA, неизменяемый image digest, staging-проверку, approval и критерий прекращения выкладки.
  2. Тег контейнера может изменяться: для повторяемого развертывания важно точно знать digest и provenance образа.
  3. Rollback приложения и откат схемы/данных — разные процессы. Откат приложения не всегда возможен после несовместимой миграции.

Три конкретных примера

1. Пример фиксации image digest

Пример: bash
docker image inspect academy-demo:local --format "{{json .RepoDigests}}"

Как интерпретировать: У локального образа без push список RepoDigests может быть пустым; это не означает, что image отсутствует.

2. Условная release-матрица

Пример: text
SHA → CI pass → image digest → staging smoke
                 → approval → release → monitor
                 → rollback if SLO violated

Как интерпретировать: Для каждого перехода укажите реальный URL или SHA: бумажный checklist без подтверждения не засчитывается.

3. Пример отчёта о выпуске

Пример: json
{"source_sha":"<sha>","image_digest":"sha256:<digest>","environment":"staging","smoke":"pending","rollback_ref":"<previous>"}

Как интерпретировать: Не размещайте рабочие учетные данные в release manifest.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Релиз — артефакт плюс протокол принятия решения

Для воспроизводимого выпуска фиксируйте commit SHA, image digest, версии схемы и набор пройденных gates. Staging позволяет проверить поведение в похожей среде, но не гарантирует совпадения нагрузок и секретов production. Approval — отдельное контрольное действие, которое связывает человека и конкретную версию артефакта.

Rollback приложения безопасен только при совместимости схемы и данных; после необратимой миграции старый бинарник может не работать. Поэтому заранее документируйте forward-compatible изменения и действия восстановления.

Release candidate:
commit: 9f1c... (пример)
image: registry.example.test/app@sha256:<digest>
db schema: revision N
smoke: PASS / 2026-10-25 (пример)
approval: pending

git rev-parse HEAD
docker image inspect academy-example:local --format '{{.Id}}'

Приём: привязывайте smoke result к digest, а не к изменяемому тегу. Ловушка: «откатили контейнер» при несовместимой схеме. Проверка: до релиза выполните dry-run совместимости старой и новой версий только в тестовой среде.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

После выкладки увеличился HTTP 5xx, хотя job CI зелёный.

Диагностическая развилка

Сопоставьте deployed digest с CI SHA, затем latency/error metrics до и после; принимайте решение по заранее заданному stop condition.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Считать тег `latest` неизменяемым идентификатором выпуска.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Опишите release gate для синтетической версии с конкретным критерием rollback и доказательством доступности предыдущего артефакта.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «После выкладки увеличился HTTP 5xx, хотя job CI зелёный.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему считать тег `latest` неизменяемым идентификатором выпуска — неверный диагностический вывод?
Показать критерий хорошего решения

Сопоставьте deployed digest с CI SHA, затем latency/error metrics до и после; принимайте решение по заранее заданному stop condition.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
