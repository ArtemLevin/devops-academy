01 · Что требуется уметь

Цель и критерий результата

Тема: Логи и traces. Измеримая цель: Проследить correlation ID через backend/worker.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Структурированный лог должен содержать timestamp, severity, service, correlation/request ID и безопасное описание события.
  2. Trace строит дерево spans: верхнеуровневый HTTP-запрос может порождать SQL-запрос и отправку фоновой задачи. ID позволяет соединить части пути.
  3. Нельзя логировать пароли, access token, персональные данные учеников или содержимое документов; используйте синтетические идентификаторы.

Три конкретных примера

1. Структурированный лог Python

Пример: python
import logging
logging.basicConfig(level=logging.INFO)
logging.info("request complete",extra={"request_id":"demo-7"})

Как интерпретировать: Базовый Formatter стандартного logging может не вывести поле extra — для JSON нужен настроенный formatter.

2. Минимальный trace-контекст

Пример: text
trace_id=7ed1 span_id=1 HTTP POST /publish
  trace_id=7ed1 span_id=2 SQL INSERT job
  trace_id=7ed1 span_id=3 QUEUE publish

Как интерпретировать: Это учебный формат; trace ID следует переносить через границы процессов в соответствии с instrumentation.

3. Найти request ID в учебном логе

Пример: bash
grep -n "request_id=demo-7" ./synthetic.log

Как интерпретировать: Работает с созданным заранее синтетическим файлом, а не с рабочими дампами.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Корреляция событий через границы процессов

Одна пользовательская операция может породить HTTP-запрос, SQL-транзакцию и Celery-задачу. Логи этих стадий связываются request/correlation ID и task ID. Timestamp помогает отсортировать события, но по одним часам сложно доказать принадлежность к одной операции, особенно при асинхронных ретраях.

Структурированный лог должен содержать событие, код результата, latency и идентификатор трассировки; не записывайте тела запросов, токены доступа и персональные данные учеников.

{"time":"2026-10-25T12:00:00Z","level":"INFO","event":"job.enqueued","request_id":"demo-27","job_id":"demo-job-27"}
{"time":"2026-10-25T12:00:02Z","level":"INFO","event":"job.completed","request_id":"demo-27","job_id":"demo-job-27"}

import logging
logging.basicConfig(level=logging.INFO, format='%(levelname)s %(message)s')
request_id = 'synthetic-req-1'
logging.info('request completed request_id=%s result=ok', request_id)

Приём: при разборе сбоя начинайте с одного request ID и проверяйте отсутствующую стадию. Ловушка: считать одинаковый timestamp достаточным для корреляции. Проверка: найдите событие enqueue и подтверждение worker с единым ID.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

API отвечает 202, а worker не завершает задачу; журналы разрознены.

Диагностическая развилка

Проверьте сохранность correlation ID между enqueue и worker execution и наличие записи о финальном состоянии.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Собирать все логи в одно место без политики маскирования данных.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Составьте минимальный JSON-лог для API и worker без секретов и покажите объединение по одному ID.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «API отвечает 202, а worker не завершает задачу; журналы разрознены.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему собирать все логи в одно место без политики маскирования данных — неверный диагностический вывод?
Показать критерий хорошего решения

Проверьте сохранность correlation ID между enqueue и worker execution и наличие записи о финальном состоянии.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
