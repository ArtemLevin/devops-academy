01 · Что требуется уметь

Цель и критерий результата

Тема: C3.9 сценарии. Измеримая цель: Повторить нагрузочный тест на эталоне.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Сценарий нагрузки должен фиксировать количество объектов, действия, продолжительность, вклад браузера и сети; иначе сравнение C3.9 невоспроизводимо.
  2. Показатель p95 определяется распределением измерений, а не максимальной секундой одного прогона.
  3. Эталон (baseline) и кандидат требуют идентичного окружения; прогрев, кеш и фоновые процессы — источники разброса.

Три конкретных примера

1. Детерминированные синтетические точки

Пример: typescript
type Point={id:string;x:number;y:number};
const points:Point[]=Array.from({length:100},(_,i)=>({
  id:`demo-${i}`,x:i%10,y:Math.floor(i/10)
}));

Как интерпретировать: Создаёт 100 одинаковых объектов для повторяемого учебного сценария; не описывает внутренний формат TutorBoard.

2. Простой расчёт квантиля в Python

Пример: python
from statistics import median
a=sorted([12,14,16,19,22,27,34,49,51,120])
p95=a[int(0.95*(len(a)-1))]
print(median(a),p95)

Как интерпретировать: Это ближайший по индексу учебный estimator; в отчёте указывайте метод расчёта перцентиля.

3. Манифест нагрузки

Пример: json
{"scenario":"C3.9-demo","objects":100,"runs":10,"browser":"<version>","hardware":"<description>","artifact":"<trace>"}

Как интерпретировать: Заполните реальными параметрами и SHA тестируемого билда; имя C3.9 взято из программы, детали реального теста требуют проверки кода.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Стандартизованный сценарий нагрузки

Сценарий C3.9 имеет смысл только при фиксированном наборе объектов, масштабе, длительности, числе участников и методе измерения. Нельзя объявлять победителя по одному прогону: browser scheduling, GC, прогрев JIT и фоновые процессы создают вариативность.

План нагрузки должен содержать разные фазы: idle, массовое построение объектов, перетаскивание, zoom и восстановление. Каждый прогон сохраняет версию приложения и конфигурацию тестовых данных.

// Синтетический генератор координат — без пользовательских данных
const points = Array.from({length: 1000}, (_, i) => ({
  id: `p-${i}`, x: i % 50, y: Math.floor(i / 50)
}));
console.log(points.length); // 1000

fixture_id: board-1000-synthetic
phases: idle(10s), zoom(20s), drag(20s)
metrics: p95_frame_ms, long_tasks, heap_mb
runs: 5 baseline + 5 candidate

Приём: сохраняйте fixture и seed вместе с результатом. Ловушка: тестировать разные графические сцены у двух версий. Проверка: повторяемость результатов внутри версии и контроль одинаковости входа.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Один прогон быстрее другого, но неизвестно, связана ли разница с кодом.

Диагностическая развилка

Сделайте серию одинаковых прогонов, контролируйте прогрев и распределение задержек, укажите количество наблюдений.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Оценивать улучшение по одному успешному запуску.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Создайте синтетический сценарий с фиксированным seed и независимыми измерениями baseline и candidate.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Один прогон быстрее другого, но неизвестно, связана ли разница с кодом.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему оценивать улучшение по одному успешному запуску — неверный диагностический вывод?
Показать критерий хорошего решения

Сделайте серию одинаковых прогонов, контролируйте прогрев и распределение задержек, укажите количество наблюдений.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
