01 · Что требуется уметь

Цель и критерий результата

Тема: Сценарии отказа. Измеримая цель: Провести воспроизводимый тест разрыва сети.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Fault injection разрыва сети выполняют в изолированной тестовой среде с синтетическими объектами и возможностью вернуться к baseline.
  2. Нужно отдельно проверять состояние канала, очередь pending, server version и отсутствие потерь/дублей после reconnect.
  3. Успех после reconnect подтверждается хешем или точным сравнением итогового состояния у двух клиентов, а не анимацией подключения.

Три конкретных примера

1. Таблица тестовых событий

Пример: text
t0: A online, B online, version=2
t1: A offline, enqueue move(id=c7)
t2: B online, add(id=c8), version=3
t3: A reconnect, reconcile, version=4
t4: A/B snapshots equal

Как интерпретировать: Это сценарий тестирования, не команда обрыва реального сетевого интерфейса.

2. Синтетический snapshot сравнения

Пример: python
import hashlib, json
def digest(state):
    data=json.dumps(state,sort_keys=True,separators=(",",":"))
    return hashlib.sha256(data.encode()).hexdigest()
assert digest({"p":2})==digest({"p":2})

Как интерпретировать: Хеш применим только к канонически сериализованному содержимому, без недетерминированных полей.

3. Критерии восстановления

Пример: text
pending queue = 0
server version = client A version = client B version
unique(command_id) = count(sent logical commands)
state digest(A) = state digest(B)

Как интерпретировать: Проверяйте и версию, и содержимое: одинаковая версия не всегда доказывает равенство данных.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

После reconnect у пользователей отличаются координаты одного объекта.

Диагностическая развилка

Сверьте версии, очередь неподтверждённых команд, повторы и итоговые снимки; приоритет — сохранить и сравнить оба состояния.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Проверять только индикатор «связь восстановлена».

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Сконструируйте учебный offline/reconnect сценарий с двумя клиентами и объективной проверкой сходимости.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «После reconnect у пользователей отличаются координаты одного объекта.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему проверять только индикатор «связь восстановлена» — неверный диагностический вывод?
Показать критерий хорошего решения

Сверьте версии, очередь неподтверждённых команд, повторы и итоговые снимки; приоритет — сохранить и сравнить оба состояния.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
