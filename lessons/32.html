01 · Что требуется уметь

Цель и критерий результата

Тема: Конфликты и undo. Измеримая цель: Проверить два клиента и конфликт версий.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Конфликт возникает, когда два клиента применяют несовместимые изменения на основе старой версии объекта.
  2. Optimistic concurrency обычно сравнивает ожидаемую версию с фактической и возвращает конфликт (например 409) при несовпадении.
  3. Undo в распределённой системе зависит от того, чью операцию и какую версию отменяют; простой возврат локального стека может стереть чужую работу.

Три конкретных примера

1. Конкурирующие изменения одной точки

Пример: json
{"client":"A","object":"p1","base_version":7,"x":10}
{"client":"B","object":"p1","base_version":7,"x":11}

Как интерпретировать: Если A уже создал version=8, операция B с base_version=7 должна пройти через политику конфликта.

2. Условный compare-and-swap SQL

Пример: sql
UPDATE demo_points
SET x=11, version=version+1
WHERE id='p1' AND version=7;
-- rowcount=0: версия уже сменилась

Как интерпретировать: Только учебная БД с синтетическими данными; проверка rowcount обязательна.

3. Матрица undo

Пример: text
A: move p1 from 1 → 10 (v7→v8)
B: move p1 from 10 → 11 (v8→v9)
A: undo? cannot blindly restore x=1

Как интерпретировать: Правило отмены требует проверки конфликтов; тестируйте итог у обоих клиентов.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Конфликт версий и пределы undo

Два клиента могут читать одну версию документа, затем параллельно отправить изменения. Если API использует optimistic concurrency, запись со старой версией должна получить явный конфликт, а клиент — процедуру перечитывания и разрешения. Без этого последняя запись может тихо затереть первую.

Undo в совместной системе сложнее локального: отмена собственной операции должна учитывать чужие последующие изменения. Выбор OT, CRDT или серверного порядка зависит от семантики операций, а не только от транспорта.

PUT /boards/demo HTTP/1.1
If-Match: "v7"
Content-Type: application/json

{"synthetic":true,"objects":[]}

Client A reads v7; Client B reads v7
A PUT If-Match v7 -> 200 / ETag v8
B PUT If-Match v7 -> 412 Precondition Failed
B reloads v8 -> resolves conflict intentionally

Приём: фиксируйте «ожидаемая версия → фактическая версия» в журнале синтетических операций. Ловушка: автоматически перезаписывать конфликт без участия модели merge. Проверка: прогон с двумя клиентами и инвариант «ни одна подтверждённая операция не потеряна».

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Пользователь А отменил действие, и объект пользователя Б неожиданно исчез.

Диагностическая развилка

Восстановите последовательность версий и ownership изменения; сравните undo на старом и актуальном состояниях.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Применять локальный undo без учета новых серверных операций.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Разработайте две конкурентные операции изменения координат и сформулируйте ожидаемый конфликт/правило разрешения.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Пользователь А отменил действие, и объект пользователя Б неожиданно исчез.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему применять локальный undo без учета новых серверных операций — неверный диагностический вывод?
Показать критерий хорошего решения

Восстановите последовательность версий и ownership изменения; сравните undo на старом и актуальном состояниях.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
