Retries и идемпотентность

Воспроизвести дублирование события без дубля записи. В этом материале разберём устройство механизма, примеры отказов и порядок подтверждения результата.

01 · Что требуется уметь

Цель и критерий результата

Тема: Retries и идемпотентность. Измеримая цель: Воспроизвести дублирование события без дубля записи.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. At-least-once доставку следует проектировать с учётом повторов: один message ID может быть обработан повторно после сбоя worker.
  2. Идемпотентность означает отсутствие дополнительного нежелательного эффекта при повторении одной логической операции; защита может опираться на UNIQUE key и транзакцию.
  3. Retry без backoff/jitter или без ограничения может создать шторм; отличайте временные сбои от постоянных ошибок контракта.

Три конкретных примера

1. Учебная таблица дедупликации

Пример: sql
CREATE TABLE demo_jobs (
  request_key text PRIMARY KEY,
  status text NOT NULL
);
INSERT INTO demo_jobs VALUES ('req-1','done')
ON CONFLICT (request_key) DO NOTHING;

Как интерпретировать: Только в тестовой базе. Повторный INSERT с тем же ключом не создаёт вторую запись.

2. Задача с явным ограниченным retry

Пример: python
@app.task(bind=True, max_retries=3)
def deliver(self, key):
    try:
        return send_once(key)  # идемпотентный тестовый helper
    except TemporaryError as exc:
        raise self.retry(exc=exc, countdown=5)

Как интерпретировать: Функции send_once и TemporaryError — псевдо-интерфейсы; реализуйте их на синтетическом стенде до запуска.

3. Контракт повторной доставки

Пример: text
attempt 1: key=A → DB INSERT → ACK lost
attempt 2: key=A → ON CONFLICT → no duplicate
assert: count(key=A) == 1

Как интерпретировать: Правило dedupe должно быть атомарным; проверяйте факт один раз, а не число попыток.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Worker обработал задание, но умер до ACK; брокер повторно отдал сообщение.

Диагностическая развилка

Проверьте уникальный ключ операции в хранилище и правило повторной доставки. Предложите границу транзакции.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Считать количество успешных executions равным количеству уникальных событий.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

На синтетической таблице покажите повторный INSERT с тем же key и докажите отсутствие дубля SQL-запросом.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Worker обработал задание, но умер до ACK; брокер повторно отдал сообщение.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему считать количество успешных executions равным количеству уникальных событий — неверный диагностический вывод?
Показать критерий хорошего решения

Проверьте уникальный ключ операции в хранилище и правило повторной доставки. Предложите границу транзакции.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
