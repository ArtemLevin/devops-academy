01 · Что требуется уметь

Цель и критерий результата

Тема: Сценарий эксплуатации. Измеримая цель: Выполнить тестовый release/monitor/rollback/restore.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Эксплуатационный сценарий release/monitor/rollback/restore должен иметь безопасный предел воздействия, наблюдаемый baseline и явное условие завершения.
  2. Мониторинг после релиза включает latency/errors и состояние фоновых задач; одни только HTTP 200 могут скрыть неработающий worker.
  3. Rollback приложения и restore данных проверяются отдельно, поскольку последствия миграций могут быть необратимы автоматическим возвратом к прежнему image.

Три конкретных примера

1. План операции для синтетического сервиса

Пример: yaml
scope: isolated-demo
baseline: "HTTP+worker smoke"
release: "candidate digest"
stop_if: "5xx ratio above threshold"
rollback: "known-good digest"
restore: "test backup only"

Как интерпретировать: Ни один пункт не разрешает автоматическое вмешательство в production; детали проверяются до запуска.

2. Сбор фактов до изменения

Пример: bash
git rev-parse HEAD
docker compose ps
docker compose config --services

Как интерпретировать: Контекст Docker и имена сервисов должны соответствовать изолированному стенду.

3. Схема контроля выпуска

Пример: text
T0 baseline → T1 candidate smoke → T2 monitor
                                  ├ OK → observe
                                  └ FAIL → approved rollback
T3 verify API + data invariants + worker task

Как интерпретировать: Сигнал FAIL заранее определён и измерен, а не выведен по ощущению разработчика.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Операционный сценарий — от решения до восстановления

Практическое сопровождение релиза — единый цикл: baseline → change plan → deployment → smoke → monitoring → rollback decision → restoration check. Каждый переход имеет условие продолжения/остановки. Успешный smoke не исключает деградации p95 при реальной нагрузке, поэтому после выпуска нужен период контролируемого наблюдения.

Все модифицирующие действия выполняются только на изолированной учебной инфраструктуре с контрольными синтетическими записями. Не инициируйте тесты отказа на реальных сервисах без отдельного согласования.

preflight: baseline PASS; backup restorable
change: candidate digest recorded
verify: HTTP + worker task + DB invariant
observe: error_rate, p95, available RAM
rollback: defined threshold + old digest
postcheck: synthetic read/write PASS

# Безопасная диагностическая стадия
docker compose ps --all
docker compose logs --tail=70 --timestamps

Приём: назначьте критерии rollback численно до эксперимента. Ловушка: считать rollback успешным только по контейнерному статусу running. Проверка: восстановление бизнес-инварианта и отсутствие побочных эффектов.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

После синтетического релиза API доступен, но очередь Celery перестала обрабатываться.

Диагностическая развилка

Проверьте queue depth и тестовую задачу; отделите rollback образа от восстановления состояния БД.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Останавливать работающий сервис до фиксации baseline.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

В отдельном стенде самостоятельно спланируйте обратимый релиз с данными до/после и проверкой двух независимых подсистем.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «После синтетического релиза API доступен, но очередь Celery перестала обрабатываться.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему останавливать работающий сервис до фиксации baseline — неверный диагностический вывод?
Показать критерий хорошего решения

Проверьте queue depth и тестовую задачу; отделите rollback образа от восстановления состояния БД.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
