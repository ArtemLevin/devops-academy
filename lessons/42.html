01 · Что требуется уметь

Цель и критерий результата

Тема: Ansible. Измеримая цель: Проверить idempotency на учебном стенде.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Ansible описывает желаемое состояние в tasks; идемпотентный playbook при повторном выполнении не должен совершать необоснованных изменений.
  2. check mode помогает предварительно оценить изменения, но поддержка dry-run зависит от используемого module.
  3. Нужны контроль инвентаря, ограничение hosts и отсутствие секретов в выводе: playbook может затронуть множество машин.

Три конкретных примера

1. Безопасная учебная задача на localhost

Пример: yaml
- hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: Assert example variable
      ansible.builtin.assert:
        that: demo_mode | default(true) | bool

Как интерпретировать: Только локальное выполнение, без remote hosts. При второй прогонке assert не меняет состояние.

2. Синтаксис и dry-run

Пример: bash
ansible-playbook --syntax-check playbook.yml
ansible-playbook --check --diff playbook.yml

Как интерпретировать: Проверьте playbook.yml на отсутствие задач с внешним воздействием; --check может быть неполным.

3. Модель идемпотентности

Пример: text
run 1: ok=3 changed=1 failed=0
run 2: ok=4 changed=0 failed=0
assert: final config equal expected

Как интерпретировать: Числа условные; именно второй фактический прогон подтверждает стабильное состояние.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Ansible: декларативная желаемая конфигурация

Ansible выполняет набор tasks по inventory. Идемпотентность означает, что повторный запуск без изменения входов не должен создавать новых изменений. --check моделирует изменения, но не все модули поддерживают его одинаково. Дрейф конфигурации проверяют повторным запуском и отчётом changed.

В учебном окружении используйте localhost с connection: local и безопасную цель, например каталог в /tmp с уникальным именем. Разрушительные операции и системные права требуют отдельного разрешения.

- hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: Ensure academy lab directory exists
      ansible.builtin.file:
        path: /tmp/academy-ansible-demo
        state: directory
        mode: '0755'

ansible-playbook --syntax-check demo.yml
ansible-playbook --check --diff demo.yml

Приём: запускайте два тестовых прогона с одинаковым inventory и проверяйте changed=0 во втором. Ловушка: shell-задача без creates/changed_when может сообщать об изменении каждый раз. Проверка: замерьте idempotency без административных привилегий.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Каждый повторный запуск Ansible сообщает changed=1 для одного шаблона.

Диагностическая развилка

Сравните дифф, случайные значения и timestamp в шаблоне; отличите реально изменённые байты от неправильного changed_when.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Считать один успешный playbook доказательством идемпотентности.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

На localhost спроектируйте playbook с двумя безопасными повторными запусками и сохраните дифф.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Каждый повторный запуск Ansible сообщает changed=1 для одного шаблона.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему считать один успешный playbook доказательством идемпотентности — неверный диагностический вывод?
Показать критерий хорошего решения

Сравните дифф, случайные значения и timestamp в шаблоне; отличите реально изменённые байты от неправильного changed_when.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
