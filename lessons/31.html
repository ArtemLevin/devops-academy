01 · Что требуется уметь

Цель и критерий результата

Тема: Непостоянная связь. Измеримая цель: Понять очереди команд и reconnect.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Offline-first клиент хранит локальные действия и синхронизирует их после reconnect. Требуется явное различение pending/acked/failed.
  2. WebSocket reconnect не восстанавливает автоматически пропущенные события; нужен cursor/version или запрос текущего состояния.
  3. Порядок и повторная доставка команд могут влиять на состояние; используйте idempotency key, версионирование и дедупликацию.

Три конкретных примера

1. Учебная структура offline-команды

Пример: typescript
type Command={id:string;boardId:string;baseVersion:number;
  kind:"move";x:number;y:number};
const pending:Command[]=[{id:"c1",boardId:"demo",baseVersion:3,kind:"move",x:2,y:4}];

Как интерпретировать: Данные синтетические; реальный контракт TutorBoard уточняют по актуальному коду.

2. Протокол reconnect

Пример: text
CONNECTED:   send command c1(version=3)
DISCONNECTED: persist c2 locally
RECONNECTED: fetch server version → reconcile → resend c2

Как интерпретировать: Повторная отправка допускает уже обработанный c2 — сервер должен распознавать его ID.

3. Правило ack

Пример: json
{"command_id":"c2","server_version":5,"status":"applied"}

Как интерпретировать: Положительный ack должен соответствовать конкретной команде и зафиксированному состоянию сервера.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Offline queue требует явной модели доставки

При кратковременной потере сети клиент доски может сохранить локальные команды и повторить отправку после reconnect. Это требует устойчивого идентификатора команды, версии документа и подтверждения сервера. Повторная доставка и перестановка сообщений способны создавать дубли и конфликты даже при исправном WebSocket.

Различайте состояния локальной команды: pending, sent, acked, failed. UI должен показывать, что данные ещё не подтверждены сервером, особенно перед закрытием вкладки.

type PendingOp = { id: string; baseVersion: number; payload: unknown };
const queue: PendingOp[] = [
  { id: 'synthetic-op-1', baseVersion: 7, payload: {kind:'move', x:1} }
];
console.log(queue.map(op => op.id));

Offline: command demo-1 -> pending
Reconnect: resend demo-1 -> server deduplicates
ACK: new serverVersion=8 -> remove pending

Приём: сохраняйте локальный operation ID до отправки и используйте его при retry. Ловушка: очищать очередь после сетевой отправки до server ACK. Проверка: симулируйте потерю подтверждения в тестовом клиенте и убедитесь, что результат не дублируется.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

После восстановления связи доска показывает старые объекты, хотя сокет reconnect успешен.

Диагностическая развилка

Сравните версию клиентского состояния и серверный cursor; проверьте replay пропущенных событий.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Считать CONNECTED WebSocket доказательством полноты синхронизации.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Опишите очередь из трёх синтетических команд, одну повторную доставку и способ доказать отсутствие пропуска.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «После восстановления связи доска показывает старые объекты, хотя сокет reconnect успешен.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему считать connected websocket доказательством полноты синхронизации — неверный диагностический вывод?
Показать критерий хорошего решения

Сравните версию клиентского состояния и серверный cursor; проверьте replay пропущенных событий.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
