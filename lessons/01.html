01 · Что требуется уметь

Цель и критерий результата

Тема: Что такое работающий веб-сервис. Измеримая цель: Объяснить клиент/сервер, HTTP и WebSocket.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. HTTP-запрос состоит из метода, target, заголовков и необязательного тела. Ответ содержит status, headers и body. Код 200 характеризует конкретный запрос и только его путь по системе.
  2. WebSocket устанавливает долгоживущее двустороннее соединение: клиент и сервер обмениваются сообщениями независимо от цикла HTTP request/response. Успешная загрузка страницы не подтверждает работу WebSocket.
  3. Наблюдаемый сценарий следует делить на получение HTML/JS, авторизацию, чтение данных, сохранение изменений и синхронизацию. На каждом этапе фиксируется отдельное доказательство.

Три конкретных примера

1. Заголовки и код успешного GET

Пример: bash
curl -i --connect-timeout 3 --max-time 10 https://example.org/

Как интерпретировать: Сохраните итоговый статус и заголовки. Доступность этого URL не свидетельствует о работоспособности POST-запросов.

2. Условный контракт изменения доски

Пример: http
POST /api/boards/42/changes HTTP/1.1
Content-Type: application/json
Authorization: Bearer <SYNTHETIC_TOKEN>

{"action":"add","id":"point-17"}

Как интерпретировать: Демонстрационный маршрут: 401 — аутентификация, 403 — авторизация, 409 — конфликт версии. Не посылайте запрос реальному API без сверки контракта.

3. Два разных канала одного пользовательского сценария

Пример: text
GET /boards/42    → HTTP 200
POST /changes    → HTTP 403
WebSocket /live  → CONNECTED

Как интерпретировать: Страница и realtime-канал доступны, но запись запрещена. Одного «HTTP 200» для объявления сервиса исправным недостаточно.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Граница протокола и граница ответственности

HTTP-запрос проходит несколько независимых стадий: разрешение имени, соединение TCP, TLS для HTTPS, отправка запроса, обработка маршрута, обращение к зависимостям и ответ. Ошибки этих стадий имеют разные признаки. 200 OK для /health доказывает лишь успешный ответ конкретного маршрута; 503 Service Unavailable означает, что HTTP-ответ был сформирован и до приложения или промежуточного HTTP-сервера запрос дошёл.

WebSocket обычно начинается с HTTP Upgrade, после согласования соединение служит двусторонним транспортом. Для совместной доски отдельно проверяются установление соединения, авторизация, доставка события и его устойчивое сохранение: наличие WebSocket ещё не гарантирует сохранности рисунка.

GET /health HTTP/1.1
Host: example.test
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"status":"ok"}

HTTP в этом примере — иллюстрация структуры обмена, а не результат обращения к реальному сервису.

curl --connect-timeout 2 --max-time 5 --silent --show-error \
  --output /dev/null --write-out 'status=%{http_code} total=%{time_total}\n' \
  https://example.org/health

Приём: измеряйте код HTTP и длительность отдельно; тайм-аут может наступить до получения HTTP-ответа. Ловушка: curl без --fail способен завершиться кодом выхода 0 даже при HTTP 404/500. Проверка: различите HTTP-код, код выхода curl и успешность бизнес-операции.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Доска открылась, но объект не сохраняется: GET 200, POST 403.

Диагностическая развилка

Разделите предположения о недостающей роли и неверном токене. Сопоставьте сессию и статусы POST/GET в инструментах разработчика.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Считать 200 OK доказательством здоровья всего приложения.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Нарисуйте 4 отдельных проверки сценария «открыть → изменить → увидеть у коллеги → опубликовать», с методом, статусом и точкой отказа.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Доска открылась, но объект не сохраняется: GET 200, POST 403.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему считать 200 ok доказательством здоровья всего приложения — неверный диагностический вывод?
Показать критерий хорошего решения

Разделите предположения о недостающей роли и неверном токене. Сопоставьте сессию и статусы POST/GET в инструментах разработчика.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
