01 · Что требуется уметь

Цель и критерий результата

Тема: Сборка evidence. Измеримая цель: Проверить артефакты, runbooks, компетенции.

Предварительные условия: тестовая среда или локальные синтетические данные, известная оболочка и подтверждённый рабочий каталог. Для внешних систем сначала сверяйте текущее состояние репозитория и официальную документацию.

Артефакт обучения: собственный прогноз → выполненная команда либо анализ кода → фактический вывод → независимая проверка → объяснение ограничений. На L3 требуется новая самостоятельная задача без подсказки.

02 · Механизмы и код

Техническое содержание

  1. Портфолио evidence должно отображать измеримые навыки, самостоятельные решения, результаты тестов и способность проверять/восстанавливать систему.
  2. Различайте демонстрацию преподавателя, выполнение по инструкции и самостоятельное выполнение в новой ситуации; только последнее может поддерживать L3.
  3. Артефакт без commit SHA, окружения, времени и вывода проверяемой операции недостаточен для строгой аттестации.

Три конкретных примера

1. Схема карточки навыка

Пример: yaml
skill: diagnose-memory-pressure
level_claimed: L2
environment: Ubuntu-WSL2
command: "vmstat 1 4"
evidence: "<redacted-output>"
independent_check: "free -m"
reviewed: false

Как интерпретировать: Заполняйте действительными свидетельствами; reviewed=false сохраняет статус до преподавательской проверки.

2. Контроль версий артефактов

Пример: bash
git rev-parse HEAD
git status --short
sha256sum synthetic-report.html

Как интерпретировать: Последняя команда читает конкретный синтетический файл. Для реального evidence используйте неизменяемую копию.

3. Матрица competency

Пример: text
Topic       Demonstration    Guided    Independent
Linux PID   observed         yes       pending
Memory      observed         yes       pending
Rollback    not tested       no        no

Как интерпретировать: Таблица иллюстрирует правила оценки, а не обновляет журнал прогресса проекта.

Каждый фрагмент показывает один проверяемый механизм. Блоки, содержащие несколько команд, изучайте и выполняйте по одной команде за раз. Учебные URL, имена и значения не являются утверждениями об актуальной конфигурации Ваших проектов.

02a · Углублённая теория и инженерные приёмы

Как устроен механизм: дополнительные примеры

Evidence должен связываться с конкретным действием

Экзаменационный пакет — индекс доказательств: исходная цель, условия среды, версия кода, прогноз, команда, stdout/stderr, проверка, вывод и ограничение. Один удачный пример может доказывать L2, но L3 требует самостоятельного решения новой задачи и объяснения выбора. При работающих приложениях фиксируйте только обезличенные синтетические данные.

Для деплоя и восстановления приложите план риска и подтверждение возможности отката; ссылки на log/run должны относиться к тому же commit SHA, что и оцениваемая работа.

skill: Linux network diagnosis
level claimed: L2
command: curl -v --connect-timeout 2 ...
stdout: sanitized evidence URI
interpretation: TCP OK; HTTP 503
independent check: server log / request ID

git rev-parse HEAD
git status --short
# Зафиксировать исходный код и локальные изменения

Приём: создавайте Evidence ID вида E-2026-10-25-06 и связывайте с lesson и test. Ловушка: скриншот зелёной галочки без параметров запуска. Проверка: другой инженер должен воспроизвести вывод по Вашему описанию.

03 · Поиск причины

Разбор конкретного отказа

Наблюдаемый симптом

Человек утверждает, что восстановил систему, но предъявляет лишь скриншот зелёного CI.

Диагностическая развилка

Проверьте сценарий восстановления, фактический restore smoke, SHA и время; CI сам по себе не подтверждает recovery.

Ограничение вывода: устанавливайте только то, что действительно следует из измерения; альтернативные причины остаются гипотезами до проверки. Типичная ошибка: Автоматически присваивать уровень по количеству выполненных занятий.

04 · Показ → практика

Протокол безопасного эксперимента

  1. Назовите оболочку, текущую среду и область воздействия. В рабочих репозиториях сначала изучите состояние без изменения данных.
  2. По первому примеру сформулируйте прогноз: какой вывод подтвердит выбранный механизм, а какой его опровергнет?
  3. Выполните одну разрешённую команду в подходящей среде. Сохраните реальный stdout/stderr и exit code.
  4. Сравните результат с трактовкой под code block, затем выполните отдельную независимую проверку. При расхождении остановитесь и исследуйте ошибку.
Safety gate: примеры с изменением файлов, контейнеров, БД, прав, сети или инфраструктуры выполняются только в изолированном учебном стенде с синтетическими данными. При риске потери данных: сначала dry run/backup/restore plan и явное согласование. Не отправляйте пароли, токены и личные данные.
05 · Самостоятельная работа

Новая задача без готового решения

Проведите аудит пяти собственных evidence и отметьте пробелы до заявки на L3.

Что сдавать

Выбранная Вами последовательность, прогноз, результат выполнения в синтетическом/читающем режиме, независимый контроль, указание возможного ложноположительного результата и безопасный способ восстановления (если было изменение).

06 · Контроль знаний

Вопросы, которые проверяют понимание

  1. Какие две разные сущности или стадии Вы должны различать в первом примере кода?
  2. Из симптома «Человек утверждает, что восстановил систему, но предъявляет лишь скриншот зелёного CI.» какие гипотезы возможны и какое наблюдение различит их?
  3. Почему автоматически присваивать уровень по количеству выполненных занятий — неверный диагностический вывод?
Показать критерий хорошего решения

Проверьте сценарий восстановления, фактический restore smoke, SHA и время; CI сам по себе не подтверждает recovery.

Нужны фактические доказательства, объяснение механизма, безопасная область воздействия и независимая проверка. Один зелёный тест не означает исправности всей системы.

L1 — воспроизводите готовое действие; L2 — решаете с опорой; L3 — сами выбираете способ для новой задачи, объясняете и проверяете; L4 — переносите навык и диагностируете риск/восстановление. Чтение учебника не присваивает уровень.
