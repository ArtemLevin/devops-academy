# Лабораторная 06 · DNS → TCP → HTTP: безопасный диагностический сценарий

**Измеримая цель:** различить получение HTTP-ответа, HTTP-ошибку приложения и отсутствие TCP-соединения, не затрагивая рабочие сервисы.

## Теория

DNS разрешает имя в записи адресов; успешный DNS-ответ **не гарантирует**, что порт доступен. TCP-соединение может быть отклонено даже при верном IP. При успешном HTTP-обмене сервер может вернуть 200, 404, 503; это разные сигналы. Код 200 для `/health` подтверждает работоспособность конкретной проверки, а не всех компонентов сервиса.

## Устройство стенда

Скрипт `http_lab.py` поднимает временный `ThreadingHTTPServer` **только на 127.0.0.1**, выбирает свободный порт автоматически, отправляет к нему три запроса и завершает сервер:

| Маршрут | Ответ | Как интерпретировать |
|---|---|---|
| `GET /health` | `200` | Данный маршрут отвечает |
| `GET /dependency` | `503` | Синтетическая недоступность зависимости |
| `GET /missing` | `404` | Нет указанного маршрута |

Все данные фиктивные; PostgreSQL, Redis, Celery и Ваши приложения не используются. Сервер служит только для демонстрации протокола и никогда не должен применяться в production.

## Практика

1. Сначала предскажите все три кода статуса и скажите, какой из них доказывает наличие HTTP-ответа.
2. В Ubuntu, из корня репозитория выполните `python3 labs/lesson06/http_lab.py`.
3. Найдите три строки `GET`, итоговый `PASS` и объясните, почему 503 и 404 не означают ошибку DNS.
4. Проверьте, что программа завершилась (новое приглашение Bash); сервер должен освободить порт.

**Возможные результаты:** `PASS` при статусах 200/503/404; `PermissionError` или `OSError` если локальный TCP-сокет не удалось создать; `URLError`/тайм-аут при невозможности соединения. В случае ошибки пришлите текст целиком и не запускайте команды повышения привилегий.

## Самостоятельная новая задача L3

В другой учебной системе `/health` отвечает 200, но `/api/reports` отвечает 503. Сформулируйте три отличные гипотезы (маршрут, зависимость, состояние worker), для каждой предложите безопасную проверку и ожидаемый результат. Где граница доказательства работоспособности самого сервиса?

## Критерии

- **L1:** запускает демонстрацию и называет коды.
- **L2:** различает транспортный сбой от HTTP-ошибки, объясняет наблюдения.
- **L3:** самостоятельно локализует новую неисправность несколькими подтверждёнными проверками.
- **L4:** переносит метод в тестовый Compose-стенд и предъявляет runbook и подтверждённое восстановление.

Откат автоматический: сервер выключается и закрывает сокет. Дополнительные сетевые эксперименты производите только в локальном учебном окружении.
